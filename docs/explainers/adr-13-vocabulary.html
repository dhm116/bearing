Proposed ADR 13 · 2026-11-12 · draft for discussion

Vocabulary as data

Bearing's kinds, fact names and the rules that connect them become versioned, published data, each with a clear owner. Adapters publish the terms they use. The operator relates them with reviewed mappings. Bearing keeps a small core vocabulary so the five questions mean the same thing everywhere.

The decision in five lines
  1. Every term has a namespaced name. Namespaces are reverse domains (io.k8s, com.github), written short when that is unambiguous: core:owned_by, github:topics, k8s:Deployment. Two adapters can no longer collide on a name.
  2. Bearing ships a core vocabulary module (core@1): today's built-in kinds and relations, kept in a source file, versioned and aligned to Backstage, W3C ORG, OpenTelemetry and SPDX.
  3. Each adapter publishes its own vocabulary module through Describe: its kinds and fields, their shapes, and the core terms it suggests they map to.
  4. Mappings and rules are records, not frozen properties. "A Deployment is a Component", "label team names the owner" and "these two fields mean the same thing" each carry an author, a status (asserted or proposed) and a time range.
  5. Every fact names its evidence: the observation and, when a rule made it, the rule and the rule's version.

We borrow the ideas of the semantic-web standards (namespaced names, SKOS's broader and exactMatch, SSSOM's attributed mappings, PROV's derivations, SHACL's shapes). We don't take on their machinery: no OWL reasoner, triple store or SPARQL. A Turtle/JSON-LD export is possible later and costs little, but nothing depends on it.

The problems we keep solving one at a time

Each of these was fixed locally when it came up. Taken together, they share one root cause.

ADR 6 · Oct 20

A small, fixed list of kinds

Eleven kinds and thirteen relations live in pkg/model/registry.go. A new domain (Vault, systemd) has nowhere to go without a Bearing release.

The meaning lives in code that only Bearing can change.

ADR 10 · Nov 1

Configured kinds, frozen once set

Operators add k8s.Service with extends. To keep answers stable, a parent can never change and a name gets one shape. Both rules are sound, but they make every early choice permanent.

A mapping is stored as a property of the kind, so it has no history of its own.

ADR 11 · Nov 6

Two sources, two names for one team

GitHub says "design" owns the frontend, PagerDuty says "UI Team". We stopped picking a winner and show both claims with their evidence.

"Who decides" was solved for identity, but not for vocabulary.

Kubernetes adapter

The adapter decides what a namespace is

It emits every namespace as an Environment. For most people the cluster is the environment. Fixing that takes a code change and a release.

The adapter assigns meaning that belongs to the operator.

ADR 12 review · Nov 10

Choosing extends later is refused

ADR 12 lets the operator decide what a kind means after install. ADR 10 refuses a changed parent, so the first edit stops Bearing from starting.

Again, the mapping is frozen into the kind.

ADR 12 review · Nov 10

Mapped field names collide

GitHub's id is a number and PagerDuty's is text. Both are called id, and ADR 10 allows one shape per name.

Names have no namespace, so every adapter shares one flat list.

ADR 12 review · Nov 10

Derived facts lack provenance

"Label team names the owner" makes a fact that no observation stated. Which evidence backs it? Is it asserted or a guess?

Rules aren't records, so a fact can't point to one.

The common root

Three things are mixed together today: names (what a term is called), meanings (what it is a type of, and what it equals) and rules (how one fact follows from another). They live in two places, Go code and one settings block, with no namespace, no version, no author and no history. Every problem above is one of those missing pieces surfacing in a new spot. ADR 13 gives each piece an owner and a record.

The pieces and who owns them

Each layer has exactly one owner, who is the only party that can change it. Everything flows down to facts, and every fact can be traced back up.

Architecture today and proposed

Store changes

  • term replaces kind and kind_predicate: one row per kind, relation or attribute. Columns: the namespaced name, the module and version that defined it, the shape (type, cardinality, conflict policy), its deprecation (deprecated_since, replaced_by, consider, reason), and its added and retired times.
  • prefix maps a full namespace (com.github) to the module that owns it, plus its short name and any aliases. Only that module may define terms in that namespace. Stored names are always full; short names exist only in config and output.
  • mapping has the same shape as identity_link: subject term, predicate (broader, exact_match, derives), object term, status, author, justification, rule version, valid_from/valid_to.
  • fact_source.rule is a new nullable column naming the mapping and version that made the fact.

No migration is needed: Bearing has no deployments yet, so the demo starts from a clean store.

What stays exactly as it is

  • Observations are append-only and remain the provenance (ADR 2).
  • Facts keep their single time axis, asserted/proposed status, confidence and closing (ADR 6).
  • Records, same_as/distinct_from links and clusters (ADR 7). These are never OWL sameAs.
  • Answers show each evidence path (ADR 11). A path can now include a rule step.
  • DuckDB stays the store (ADR 5). Moving from kind to broader term is the same recursive CTE as today's WithDescendants.

How the core vocabulary is maintained and used

The core vocabulary becomes a source file. It is reviewed like code, versioned like an API, and generated into what the server and others consume. It stays small on purpose: only terms the five questions (and their near neighbours) need.

Rules for the core

  • It only grows. A term is never deleted or reshaped. A rename adds the new term and marks the old one deprecated and replaced_by the new. Ingest stores facts under the current name, so queries and "what changed" don't see noise when a version changes. See deprecation and supersession.
  • It is aligned, not invented. Each core term lists exact_match or close_match links to the standards people already use. Backstage's catalog is the closest model to ours, so it comes first; then W3C ORG for teams, OpenTelemetry for service.* and k8s.* names, and SPDX/purl for packages. These links are documentation and help with export. They don't change answers.
  • It stays small. A new core term needs a question that uses it. Everything else belongs in an adapter's namespace.
# vocab/core.yaml (sketch)
module: core
version: 1.3.0
terms:
  - name: Component
    is: kind
    label: A deployable piece of software
    exact_match: [backstage:Component]
    close_match: [schema:SoftwareApplication]

  - name: owned_by
    is: relation
    domain: [any]
    range: [Team, Person]
    cardinality: many
    conflict: set
    exact_match: [backstage:spec.owner]

  - name: runtime
    is: attribute
    type: object
    cardinality: many

  - name: language_version      # superseded: one successor
    is: attribute
    deprecated:
      since: 1.3.0
      replaced_by: runtime
      reason: "runtime holds language and version together"

How adapters publish their vocabulary

An adapter describes the terms it uses, in its own namespace, when the server first calls Describe. Today that call already returns fields and kinds, so the change is one new message, not a new call. The adapter may suggest how its terms relate to the core. A suggestion arrives as a proposed mapping that only the operator can accept.

The rules the server enforces

  • Namespaces are reverse domains. Describe must name a full namespace such as io.k8s; a bare k8s is refused. The first source to publish a namespace owns it, unless settings pin it to a source. Another adapter that publishes io.k8s: terms is refused, by name. Two Kubernetes adapters for two clusters share one module and differ only by instance.
  • Short names resolve by the last segment. k8s:Deployment means io.k8s:Deployment while only one loaded namespace ends in k8s. If a second one arrives, config that uses the short name fails to load, naming both, and the operator adds an alias. Stored data is unaffected, because it always holds full names. core is reserved for com.dougmccall.bearing.core.
  • Aliases are the operator's. Settings may define alias: { gh: com.github }. An explicit alias wins over a short name.
  • Shapes are per term. github:id (number) and pagerduty:id (text) are different terms, so they can't collide. A term may share a shape with a core term only through an exact_match mapping, and boot checks that the two shapes agree.
  • Grow-only per term, as ADR 10 has it today, but scoped to the term rather than the whole kind. Renames use deprecated with replaced_by.
  • Adapters never emit core terms directly. That rules out the Kubernetes adapter deciding a namespace is an Environment. ADR 12's generic adapter needs no special rule for this; it is the same rule.
  • Each observation names its module version (k8s@0.4) as a field outside the content-derived ID, so deduplication isn't affected.

How mappings and rules are defined, managed and maintained

One mechanism covers all three kinds of mapping. Each is a row with a subject, a predicate and an object, plus who made it, why, how sure, and when it was in force. This is the SSSOM pattern, and it is how Bearing already treats identity links (ADR 7).

PredicateMeansExampleEffect on answers
broaderIs a type of (today's extends)k8s:Deployment broader core:ComponentDeployments answer "who owns service X"
exact_matchSame meaning, same shapegithub:Team exact_match core:TeamQueries for core:Team include GitHub teams
close_matchRelated, for people to readk8s:Namespace close_match core:EnvironmentNone: documentation only
derivesA rule that makes a fact from an observation, with a Go template for the keyk8s:Deployment derives core:owned_by → core:Team key 'team:{{ .labels.team | lower }}'Creates facts that cite the rule and its version

Where rules run and how they change

  • In the server, at ingest. One place, every adapter, no adapter release. The observation is still the evidence; the rule is named next to it.
  • Asserted or proposed. A derives rule built from a fixed field (a label, an annotation, a URL parsed by a known rule) is asserted, as ADR 2 says. Anything that guesses, such as name similarity or a model, may only produce proposals.
  • Changing a rule is a new version, and v2 supersedes v1. A fact that v2 also makes keeps its identity and gains v2 as a source, so it doesn't close and reopen. Only facts that differ close or open. "What changed" shows the rule change next to them. See deprecation and supersession.
  • Adding broader later is allowed. It is a dated row now, not a frozen parent, so the ADR 12 blocker goes away. ADR 10's concern, that answers could change with no new evidence, is met because the mapping row is the evidence: it has an author and a date.
  • Rules use Go templates with Sprig's functions. A template sees only the fields the observation carries, which are already allow-listed, so it can't reach a secret the adapter dropped. The function set is a deterministic subset with Sprig's names (see Sprig, measured), with no env, random values, UUIDs, clocks or key generation. Those would leak secrets or make the same observation give a different fact on replay. Templates are parsed at boot, and a bad one stops boot, naming the rule. A template that renders empty, or reads a missing field, makes no fact. The template text is part of the rule, so editing it is a new version.
  • Every mapping ends at a core or operator term. No mapping goes from one adapter's term to another adapter's term. Each adapter maps to the core, which costs one mapping per term instead of one per pair. Allowing adapter-to-adapter mappings would need a real use case first.
  • Middleware stays for what templates can't express, such as parsing DATABASE_URL into depends_on. It runs inside the adapter process (ADR 12's Use), so the server needs no plugin system, gRPC callback or WebAssembly. It emits terms in the adapter's own namespace, so the operator still maps them.
# settings file: operator-owned mappings (sketch)
kind: Mapping
spec:
  id: k8s-deployment-is-component
  subject: k8s:Deployment
  predicate: broader
  object: core:Component
  justification: "Each Deployment is one service at Acme"
---

  id: r-team
  version: 2
  subject: k8s:Deployment
  predicate: derives
  object: core:owned_by
  target:
    kind: core:Team

# or from the CLI, through the event log:

# bearing vocab accept <id> --why "..."

Operator vocabulary: terms no adapter publishes

Sometimes the org's own idea of a thing is missing from every tool. In one real org, a single PagerDuty service stands for several real services, which share its on-call schedule and escalation policy. No adapter can publish that grouping, because no single tool holds it. The core shouldn't either, because it is one org's convention.

So the operator is a third owner of terms, with the same rules as the other two:

  • Its own namespace, a reverse domain such as com.acme. It can't add terms to a core or adapter namespace.
  • A pinned, verified source. The settings file names the vocabulary file's repo, path and full commit SHA, and may add a SHA-256 checksum of the file. Branch and tag names are refused. Bearing always reads a local copy of the file, then verifies it one of two ways:
    • By commit, when the repo can be reached: the file must be exactly the blob at that commit and path.
    • By checksum, when it can't, which covers fully offline installs: the file must match sha256.
    If neither check can run, or one fails, boot stops and names the file. Each term row records the repo, commit, checksum and which check passed. bearing vocab check prints the checksum to paste into settings.
  • Grow-only, with deprecation, exactly like core and adapter terms. Boot compares the new file with the terms already stored.
  • Never through import. An import still only adds mappings.

Core and adapter modules carry the same source field: the Bearing release commit for core, and the adapter's build commit, which Go records in every binary. So every term, whoever owns it, points back to a commit.

# settings file
kind: Vocabulary
spec:
  namespace: com.acme              # short name: acme
  source:
    repo: github.com/acme/bearing-vocab
    path: vocab/acme.yaml
    ref: 3f9c2e1d8a7b6c5d4e3f2a1b0c9d8e7f6a5b4c3d  # full SHA
    sha256: 9a7f0c...e41b       # optional; required offline
---
# vocab/acme.yaml, at that commit
version: 1.0.0
terms:
  - name: ServiceGroup
    is: kind
    description: "One on-call service that stands for several real services"
---
# settings file: operator mappings that use it
kind: Mapping
spec:
  id: pd-service-is-group
  subject: pagerduty:Service
  predicate: broader
  object: acme:ServiceGroup

Deprecation and supersession

A deprecated term, mapping or rule stays readable forever, but it says one of three things about what comes next. The difference matters because only the first case is safe for Bearing to act on by itself.

FieldMeaningWho may set it
sinceThe module version, or the time for a mapping, when it was deprecatedThe item's owner
replaced_byExactly one successor with the same meaning and a compatible shape. Boot checks the shapesThe item's owner
considerCandidates for a person to pick from, when no single successor fitsThe item's owner
reasonWhy, in a sentence. It appears in bearing vocab review and in answers that touch the itemThe item's owner
  • The owner decides. Bearing maintainers deprecate core terms, adapter authors deprecate their own terms, and the operator deprecates mappings and rules. A replaced_by across owners (an adapter term replaced by a core term) is only a suggestion, and arrives as a proposed mapping.
  • Chains collapse. If A is replaced by B and B by C, ingest goes straight to C. Boot refuses cycles.
  • Rules depending on a deprecated term are flagged. bearing vocab review lists them with the successor or candidates, so the operator can update them.
# a rule superseded by a different rule
kind: Mapping
spec:
  id: r-team
  version: 2
  subject: k8s:Deployment
  predicate: derives
  object: core:owned_by
  deprecated:
    since: 2026-12-01T00:00:00Z
    replaced_by: r-owner-annotation
    reason: "Ownership moved to the bearing.dev/owner annotation"
# how it exports (OBO and Dublin Core conventions)
core:language_version
    owl:deprecated true ;
    dct:isReplacedBy core:runtime .

k8s:labels
    owl:deprecated true ;
    oboInOwl:consider k8s:label_team, k8s:label_app .

Facts made by a superseded rule carry over when the successor makes the same fact: the fact gains a new source row instead of closing and reopening. So swapping a rule changes "what changed" only where the answer really changed.

Import and export: exactly what is supported

There are two different questions here, and they have different answers. Where can a term come from? Only from an owner that versions it, deprecates it and sends data under it: a Bearing release (core) or an adapter's Describe. Where can a mapping come from? From anyone, but only the operator makes it count. So the adapter row in the ownership table ("terms in its own namespace, their shapes, and suggested mappings") and "import never defines terms" don't conflict. An adapter's terms arrive through Describe, not through bearing vocab import. Import is a door for mappings only.

Why import can't define terms. A term from a file would have no owner Bearing can hold to the grow-only and deprecation rules, and no adapter would ever send data under it, so it would be an empty name. An imported OWL class hierarchy would also bring open-world meaning and inheritance chains that Bearing doesn't evaluate. One side of an imported mapping may be outside Bearing, though: ent:Application exactMatch core:Component is kept as an alignment, so an org's own names show up beside the term and survive a round trip.

What this changes, and what it deliberately doesn't

Changes

  • ADR 10 is amended. extends becomes a broader mapping row that can be added and retired with dates. "One shape per name" becomes "one shape per namespaced term". Grow-only applies per term.
  • ADR 12 gets simpler. All three review blockers are answered by this ADR instead of by special rules for the generic adapter. The generic adapter publishes a module built from the mapping; init writes its suggestions.
  • The Kubernetes adapter stops emitting Environment. It suggests k8s:Namespace broader core:Environment and leaves the choice to the operator.
  • Proto: a VocabularyModule message in DescribeResponse, plus a module version on observations. Both are additive, so the protocol version stays the same.
  • The demo ships suggested mappings for Acme, so the five questions still work out of the box. The golden tests pin core@1, the Acme mappings and the fixtures.

Deliberately not doing

  • No OWL reasoning. It is open-world, so it can't say "no owner". Its sameAs merges things irreversibly, and that would undo ADR 7.
  • No triple store or SPARQL. DuckDB answers every question with the tables above.
  • No external upper ontology as the base. The Computer Science Ontology classifies research topics, and schema.org has no ownership or dependency terms. We align to standards; we don't inherit from them.
  • No per-observation ontology versions in queries. Ingest stores facts under the current term, and the version is kept for lineage only.
  • No mappings between two adapters' terms. Everything maps to a core or operator term, until a use case justifies more.
  • No import that defines terms. Terms come only from core releases and adapter modules. Import adds mappings and alignments, always as proposals.

Order of work

  1. ADR 13 accepted; amend ADR 10 in the same PR.
  2. Namespaced terms, plus vocab/core.yaml and its generator, replacing registry.go's tables. No behaviour change: the core terms map one to one.
  3. term, prefix and mapping tables, and fact_source.rule. extends moves to broader rows.
  4. VocabularyModule in Describe; the three adapters publish modules; Acme ships suggested mappings.
  5. derives rules at ingest, plus bearing vocab review|accept|reject.
  6. ADR 12's generic adapter, built on all of the above.
  7. With step 5: bearing vocab export|import --format yaml for mapping packs. Later, if asked: Turtle and JSON-LD.

Still open

  • How is a service linked to the PagerDuty service that covers it? PagerDuty answers on-call questions, not ownership: "who can help with payments-api right now?" and "who was on call for it during the 2026-03-04 incident?" (Ownership is already handled per path by CODEOWNERS.) Usually no source states the link outright. It has to be followed as a trail of clues, any of which can be broken:
    • A Datadog monitor is tagged service:payments-api, which proposes that the monitor watches that Kubernetes service.
    • The same monitor's message notifies @pagerduty-Checkout, which proposes that it pages the PagerDuty service Checkout.
    • Together they propose that payments-api is covered by Checkout. A stale handle or a tag naming nothing breaks the chain, and the break is visible.
    Each step is a proposed fact made by a rule and cites its observation (ADR 2). The joined link is a proposal whose evidence is the whole path (ADR 11). The operator confirms it either up front, from a review list, or on demand, when an answer shows "probably Checkout, via monitor 123, unconfirmed". Confirming writes an asserted fact authored by the operator, through the event log, the same way bearing link accept works for identity links. Other trails can back the same link: a Terraform or Crossplane definition of the monitor, or code in a repo that emits the metric the monitor watches. Or no trail exists at all, and then only the operator can supply the link. This is ADR 7's machinery applied to a relation instead of same_as:
    • Candidates are paths through proposed and asserted facts.
    • Scoring uses transparent features, plus a System One model's calibrated judgement for the fuzzy hops, such as whether @pagerduty-checkout is the service "Checkout Platform".
    • Each independent observation reinforces the link; contrary evidence and time weaken it.
    • A person promotes it.
    One subtlety: independence is judged per claim, not per observation. A Terraform definition and the Datadog API describing the same monitor are the intent and the outcome of one claim: what the monitor is configured to do. They back that step once, and they are not two reasons to believe the service is covered. But the same Terraform observation can make a different claim, such as referring to the repository that payments-api comes from. That is a second path from the service to the monitor, and it does count as separate confirmation. So one observation can support several steps, several observations can back one step, and the proposal's score combines its steps: alternative paths for the same step add up, while a step every path shares counts once. ADR 13 only needs derives rules that can emit proposed facts. Joining hops into a proposed relation belongs in its own ADR, extending ADR 7's matchers.

Three ways to do it

  • Import Sprig, use its hermetic map. 193 functions and no code to write, but 10 new modules, about 10,400 lines we depend on, and a deny-list for the 14 functions above.
  • Import Sprig, and pick the functions we allow. The same dependencies, because Go compiles in the whole package, but fewer functions to reason about.
  • Copy the functions rules need, keeping Sprig's names. A 55-function set covers strings, regex, lists, dicts, defaults, URL and path parts, JSON, base64 and sha256sum. That is about 460 lines of Sprig, which is MIT-licensed, so we keep its notice. Only 6 of the 55 reach a dependency. Case conversion (snakecase, kebabcase, camelcase) is about 40 lines to rewrite; int becomes strconv; semver and semverCompare reuse the version comparison already in pkg/query. That means no new modules.

Recommendation: copy. About 500 lines plus table tests, in code that rarely changes, beats ten modules and a deny-list. Templates keep Sprig's names, so anyone who knows Helm can write them, and a missing function can be added when a rule needs it.
